# Bedrock packet codec

`Bedriox\Protocol\Packet` is the sole Minecraft Bedrock packet surface used by Bedriox. `ProtocolVersion` centrally declares Minecraft 1.26.50 / protocol 2193 as the wire authority; Minecraft 1.26.51 is a qualified same-protocol retail client. Packet class and namespace names intentionally do not repeat that number.

The packet set covers discovery-adjacent network settings, login and authentication envelopes, encrypted resource-pack negotiation, StartGame, player-list and classic-skin records, empty-hand AddPlayer with synchronized actor data, actor removal, generic LevelChunk columns, requested SubChunk responses, registry packets, movement, chat, radius negotiation, and local-player initialization. `BedrockPacketCodec` is its only packet registry. `BedrockEncryptor`, `BedrockDecryptor`, and `BedrockEncryptedEnvelopeCodec` own continuous encrypted framing.

The fixed-flat profile sends a complete typed survival game-rule snapshot in both StartGame and the initial game-rule update. Its StartGame factory accepts the authoritative player position and rotation, signed 64-bit world seed, and signed 32-bit world-spawn block coordinates; defaults remain zero rotation, seed `0`, and spawn `(0, 64, 0)`. It advertises the new inventory system so retail clients use the server-authoritative `ItemStackRequest` conversation for ordinary moves and splits instead of legacy prediction-only transactions. StartGame also carries a bounded list of data-driven block-property network-NBT compounds and the required data-driven experiments. Item registry entries always carry a network-NBT root named for their item identifier, even when that compound has no children. Biome definitions preserve their admitted string tags through the packet string table. Initial self actor data is a typed, ascending snapshot containing collision and nametag flags, health, air and maximum air, lead state, scale, and standing dimensions.

The supported release includes a tagged resource-pack response, StartGame editor settings, signed world-spawn block coordinates, a byte-sized permission level, the ItemV4 empty descriptor including its empty stack-network ID, optional chunk and teleport fields, per-entry player-list actions, the current classic-skin representation, and PlayerAuthInput's bounded list of input enum values plus explicit optional-field presence markers.

Bidirectional packet 93 carries a bounded `PlayerSkin` value alongside its authenticated player UUID and the current new/old skin-name fields. Bedriox accepts this normal appearance synchronization only for the spawned session's authenticated identity.

The player-list skin binding retains the verified login `ProfileHash` and serializes the current string-valued trusted-skin flag. Available actor identifiers are generated as bounded network NBT from the actor types the server can actually spawn. `PalettedStorage`, `ChunkSectionData`, `ChunkColumnData`, and `ChunkSerializer` form the generic full-column boundary: callers supply runtime-ID palettes and X-Z-Y indexes, contiguous signed-Y sections, one biome storage for every dimension section, and optionally bounded network-NBT block-entity roots. The serializer chooses the smallest supported `1/2/3/4/5/6/8/16`-bit layout, uses padded words where Bedrock requires them, emits v9 absolute section Y, and applies safe biome copy-last framing. Border blocks are always encoded with a zero count because non-empty Education border arrays are unsafe for retail clients. The fixed-flat factory delegates to this same serializer while preserving its qualified conservative two-bit biome form. Requested later empty sections use the all-air result, and both height maps use protocol 2193's sixteen length-prefixed 16-byte pieces. Chunk caching and blob IDs remain disabled.

Client-data verification retains the signed token's bounded, self-reported `DeviceOS` as a private `DeviceOs` value. Signature verification proves which authenticated client supplied the claim, not that the physical-device claim is truthful. Peer-facing `PlayerListAddEntry` and `AddPlayerPacket` use the distinct current `BuildPlatform` wire enum; undefined value `0` is rejected, and callers that intentionally avoid device disclosure use `BuildPlatform::Unknown` (`-1`).

`ChunkColumnData` requires its included block sections to start at `minSectionY` and remain contiguous through the highest transmitted section. Its biome list covers the complete declared `minSectionY..maxSectionY` range even when no block sections are transmitted. Each block and biome storage contains exactly 4,096 cells; block sections may contain up to eight layers. Runtime IDs must already have been translated for the active protocol by the consumer. `ChunkSerializer::section()` can also serialize one generic section for a SubChunk response.

`InteractPacket` recognizes the current vehicle-exit, mouseover, NPC-open, and inventory-open action domain (`3` through `6`) and preserves the optional target position. In particular, the ordinary inventory notification is the exact three-byte payload `06 00 00` for target runtime ID zero with no position. Unknown actions, partial positions, non-finite coordinates, trailing bytes, and truncations fail deterministically.

`ActorMetadataCollection` provides the one bounded, strictly ascending synchronized-data list used by both `AddPlayerPacket` and `SetActorDataPacket`. Supported values are byte, little-endian short, ZigZag integer, little-endian float, bounded UTF-8 string, ZigZag long, and three little-endian float vectors. `PlayerActorMetadata::baseline()` emits the complete initialized player snapshot: semantic visibility, climbing, breathing, collision (bit 48), and affected-by-gravity (bit 49) flags; the second flag word; health, color, nametag, full air and maximum air, leash state, scale, standing dimensions, always-visible nametag, zero freezing strength, and the player collision-box vector. The adjacent bit 47 is `LINGER` and must not be substituted for collision. `AddPlayerPacket` embeds that snapshot when a peer first becomes visible; later `SetActorDataPacket` instances carry state changes. Actor-property collections remain explicitly unsupported and must be empty.

`PlayerAuthInputPacket` exposes the current input-data indexes through `PlayerAuthInputFlag` while retaining the bounded raw integer list for wire inspection. `hasInput()` performs typed membership checks; `jumpHeld()`, `jumpPressed()`, and `jumpReleased()` distinguish held and edge-triggered jump state. Horizontal and vertical collision values are client hints only and never authoritative collision results. `predictedVelocity()` names the packet's Pos Delta field accurately: it is the client's predicted velocity at the end of that input tick, not a trusted displacement. The unsigned `tick` remains an `UnsignedLong`; consumers can use `UnsignedLong::compareTo()` for monotonic admission without lossy signed conversion. Protocol 2193 encodes the input-data count and each optional action with one presence marker.

`CorrectPlayerMovePredictionPacket` (161) is the protocol-2193 server-with-rewind response for rejected client movement. It preserves the prediction type, finite position/delta/rotation values, the vehicle-only optional angular velocity, authoritative on-ground state, and the unsigned processed input tick. `MovePlayerMode::RESET` remains represented for compatibility with the older packet surface, while `TELEPORT` is reserved for actual teleports and carries the additional teleport cause and source fields.

Input data may be empty, which projects to an empty flag list. Known flags are unique and bounded to the current 66-entry domain. Item interaction, stack request, block action, vehicle rotation, and predicted-vehicle fields each use one current optional discriminator. Block-action lists and packed item-use transactions decode into bounded typed values; their inventory actions retain the typed source, slot, before-stack, and after-stack rather than only a count. Unsupported action variants, vehicle payloads, and malformed conditional presence fail closed. The packed item descriptor has one optional signed stack-network-ID VarInt after its presence boolean; no additional variant discriminator exists in protocol 2193. Outbound encoding rejects flags whose required conditional payload is not implemented.

`InventoryTransactionPacket` (30) provides a state-free typed boundary for the current normal, mismatch, item-use, item-use-on-entity, and item-release variants. It caps inventory actions at 100, legacy slot sets at 1,024, each legacy byte list at 89 bytes, and item user data at 100 KiB. Request-ID-dependent legacy presence, source container/flag presence, every enum, finite vectors, descriptor scalar ranges, exact termination, and all list and byte lengths are validated before a value is returned. Decoding does not authorize an inventory mutation; Bedriox remains responsible for rejection and simulation policy.

`InventoryContentPacket` (49) sends up to 128 typed network item descriptors followed by the required full-container name and storage item. Its existing integer slot-count constructor remains available and preserves the retail-qualified empty snapshot bytes; `emptySlot()` exposes that same established descriptor to typed snapshot builders. `InventorySlotPacket` (50) sends one authoritative slot correction with independently optional full-container-name and storage-item values in the exact current order. Both values have exact, bounded decoders for fixture and consumer verification. `FullContainerName` bounds the protocol-2193 container-name ID and optional little-endian dynamic ID. These clientbound packets describe server-owned state only; they do not make client inventory claims authoritative.

Routine spawned-client coverage includes typed, closed codecs for `PlayerActionPacket` (36), `ContainerOpenPacket` (46), `ContainerClosePacket` (47), the exact-empty `ServerSettingsRequestPacket` (102), `NetworkStackLatencyPacket` (115), and `RequestAbilityPacket` (184), in addition to `MobEquipmentPacket` (31), `AnimatePacket` (44), and `ClientCacheStatusPacket` (129). Mob equipment carries the shared bounded `InventoryItemStack`, three unsigned slot/container bytes, and an unsigned actor runtime ID. Its canonical empty descriptor has a zero item ID and zero stack size; decoding non-empty equipment remains a notification and grants no inventory authority. Container-open retains the unsigned dynamic container ID, the closed current signed container-type domain, signed block position, and signed actor unique ID; `mainPlayerInventory()` selects type `INVENTORY` (`-1`) at `(0,0,0)` without inventing authority. A decoded server-settings request is only a notification and does not imply a response. `PlayerActionType` exposes the current action domain and retains both block positions and the face as untrusted notification data. `BlockPosition` bounds every coordinate to signed 32-bit wire space. Player action and ability requests never grant authority by being decoded.

`EmoteListPacket` (152) is available in both directions and preserves the actor runtime ID plus a list of canonical emote-piece UUIDs. The list is capped at 4,096 entries before allocation, each UUID is structurally validated, and truncation or trailing data fails deterministically. Decoding this packet communicates no authority and does not prescribe whether the runtime stores or broadcasts the advertised list.

`EmotePacket` (138) preserves the actor runtime ID, bounded UTF-8 emote/XUID/platform strings, unsigned tick duration, and the two known flag bits as typed values. It is a bidirectional notification; decoding a request does not authorize broadcast. `LevelEventPacket` (25) carries a signed event ID, finite three-float position, and signed event-specific data without assigning gameplay meaning to the open integer event domain. `UpdateBlockPacket` (21) carries a signed block position, already-translated unsigned runtime ID, the five known update flags, and an unsigned layer. Level events and block updates are clientbound output surfaces here; world mutation and audience selection remain server responsibilities. All three codecs require exact payload termination and reject unknown flag bits.

`RemoveActorPacket` (14) carries exactly one signed VarLong actor unique ID. It removes the matching peer actor from a client's world view; world membership, audience selection, player-list removal, and disconnect cleanup remain server responsibilities. Its decoder rejects truncated, overflowing, non-canonical, and trailing data.

`MoveActorAbsolutePacket` (18) is the peer-actor movement surface. It carries an unsigned actor runtime ID, the four current typed header flags (on-ground, teleported, force-move, and force-completion), three finite position floats, and pitch/yaw/head-yaw byte angles. Unknown header bits, non-finite coordinates, malformed variable integers, truncation, and trailing bytes fail closed. `SetActorDataPacket::playerPosture()` composes sneaking and sprinting with the complete baseline player flags, ensuring a posture update cannot accidentally clear breathing, collision, gravity, name, or climbing behavior.

Container identifiers retain their unsigned wire byte; `signedContainerId()` exposes the conventional `-1` sentinel without changing the encoded value. A latency packet preserves its full unsigned 64-bit creation time and the schema-defined `fromServer` flag; `serverResponse()` produces the corresponding server-marked value, but response policy belongs to the runtime. `AnimatePacket::isSwing()` identifies an ordinary swing notification without prescribing broadcast behavior. Request-ability values retain their typed unset, boolean, or float discriminator, accept the current ability-index domain `0..19` including vertical fly speed, reject index `20`, and require a finite float. The survival ability factory declares all current capabilities in its set mask and supplies all three speed floats, while enabling only ordinary survival interaction bits `0..5`; flying, may-fly, no-clip, and speed-capability bits are not ability values. The server may safely ignore requests or return its authoritative state.

`InteractPacket` accepts the bounded action-byte domain `0..6`. Established Bedrock implementations and retail traffic use both compact ordinal and retained legacy-valued notifications. The minimal runtime treats every decoded interaction as a notification-only no-op, so this conservative domain does not grant interaction authority. Target ID, optional position, finite floats, and exact payload termination remain mandatory.

The movement projection and standalone packet 147 retain complete typed take, place, and swap requests: bounded amounts, full source and destination container names, byte slots, and fixed little-endian stack-network-ID variants. Drop, destroy, and consume remain typed rejection-only actions; crafting bodies fail closed. Both packet forms preserve bounded filter strings and the optional text-processing origin, while the legacy request-ID projection remains available to consumers. `ItemStackResponsePacket` encodes protocol-2193 success or error entries; successful entries may carry authoritative affected slots grouped by full container name, including requested/actual slots, count-dependent stack-network IDs, redactable custom names, and bounded durability correction. These values describe intent and reconciliation only; Bedriox owns validation, atomic mutation, stack-ID allocation, and rejection sync. Packet 307 `SetPlayerInventoryOptionsPacket` remains notification-only. Successful unit vectors and schema conformance do not by themselves qualify a retail client; Bedriox owns that end-to-end qualification.
