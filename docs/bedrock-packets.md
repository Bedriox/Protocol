# Bedrock packet codec

Failed item-stack request actions carry a bounded decode location and fixed category for diagnostics. These values contain no packet bytes or item content. Protocol 2193 action bodies carry a second action byte that uses the action enum ordinal; it is not always equal to the preceding wire discriminator. The codec checks the current mapping and emits the matching marker for supported actions.

Creative item-stack requests may carry the protocol-2193 deprecated craft-results action in either standalone packet 147 or the request embedded in player-auth input. The codec preserves bounded result descriptors and user data but does not assign them inventory authority; the server decides whether a request succeeds.

`CraftingDataPacket` (52) carries an immutable replacement snapshot of at most 8,192 recipes. It supports the current shaped, shapeless, user-data-aware shapeless, chemistry, and multi recipe sections, canonicalizes recipes into wire-section order, and requires unique positive network IDs. Recipe values retain bounded identifiers, `1x1` through `3x3` grids, exact and tag ingredients, item results, UUIDs, station tags, priorities, symmetry, and unlocking requirements. Deferred workstation and mixing sections remain explicitly empty until their complete typed contracts are admitted.

The item-stack request conversation names every current crafting action discriminator and enum marker. Personal and workbench crafting use typed recipe, automatic-recipe, created-output, consume, transfer, and advisory-result actions. Optional recipe, repair/disenchant, loom, and retained no-payload actions are also structurally bounded so normal current traffic remains aligned for consumer policy. All client recipe IDs, craft counts, ingredient descriptions, result descriptions, filter indexes, and costs remain untrusted intent; Protocol never decides whether a recipe matches or changes inventory state.

`FullContainerName::CRAFTING_INPUT`, `CRAFTING_OUTPUT`, and `CREATED_OUTPUT` name the current request containers without consumer-owned numeric IDs. `ContainerType::Workbench` uses the existing bounded open/close conversation; opening a screen does not create a container session or grant access authority.

`Bedriox\Protocol\Packet` is the sole Minecraft Bedrock packet surface used by Bedriox. `ProtocolVersion` centrally declares Minecraft 1.26.50 / protocol 2193 as the wire authority; Minecraft 1.26.51 is a qualified same-protocol retail client. Packet class and namespace names intentionally do not repeat that number.

The packet set covers discovery-adjacent network settings, login and authentication envelopes, encrypted resource-pack negotiation, StartGame, player-list and classic-skin records, empty-hand AddPlayer with synchronized actor data, actor removal, generic LevelChunk columns, requested SubChunk responses, registry packets, movement, chat, radius negotiation, and local-player initialization. `BedrockPacketCodec` is its only packet registry. `BedrockEncryptor`, `BedrockDecryptor`, and `BedrockEncryptedEnvelopeCodec` own continuous encrypted framing.

The fixed-flat profile sends a complete typed survival game-rule snapshot in both StartGame and the initial game-rule update. Its StartGame factory accepts typed player and level `GameType` values, the authoritative player position and rotation, signed 64-bit world seed, and signed 32-bit world-spawn block coordinates; both game types default to survival, rotation defaults to zero, the seed defaults to `0`, and spawn defaults to `(0, 64, 0)`. The resulting packet retains both typed game modes for consumer inspection without attempting to decode the otherwise opaque fixed-flat payload. Its synchronized player-movement settings retain 40 ticks of rewind history by default and advertise server-authoritative block breaking. The history value is explicitly bounded to the non-negative signed 32-bit wire domain. It advertises the new inventory system so retail clients use the server-authoritative `ItemStackRequest` conversation for ordinary moves and splits instead of legacy prediction-only transactions. StartGame also carries a bounded list of data-driven block-property network-NBT compounds and the required data-driven experiments. Item registry entries always carry a network-NBT root named for their item identifier, even when that compound has no children. Biome definitions preserve their admitted string tags through the packet string table. Initial self actor data is a typed, ascending snapshot containing collision and nametag flags, health, air and maximum air, lead state, scale, and standing dimensions.

The supported release includes a tagged resource-pack response, StartGame editor settings, signed world-spawn block coordinates, byte-sized ability permission levels, the ItemV4 empty descriptor including its empty stack-network ID, optional chunk and teleport fields, per-entry player-list actions, the current classic-skin representation, and PlayerAuthInput's bounded list of input enum values plus explicit optional-field presence markers. `PlayerPermission` and `CommandPermissionLevel` close the UpdateAbilities permission domains. `Ability` names all current mask bits `0..19`; `AbilityLayer::fromAbilities()`, `maskOf()`, `supports()`, and `enabled()` construct and inspect masks without consumer-owned bit shifts while the established integer-mask constructor remains wire compatible. The survival factory projects members as player permission `1`, command permission `0`, and ability values `0x3f`; operators use player permission `2`, command permission `1`, and ability values `0xff` while retaining the same capability mask and movement speeds.

The command conversation uses `AvailableCommandsPacket` (76), `CommandRequestPacket` (77), `CommandOutputPacket` (79), and `UpdateSoftEnumPacket` (114). For protocol 2193, a command origin contains a bounded string origin tag, UUID, bounded request ID, and an unconditional signed little-endian 64-bit player actor ID. `CommandOriginType` maps the admitted wire tags to a closed semantic enum; unknown tags fail closed. Permissions, output modes, argument types, parameter options, and soft-enum update operations likewise use closed enums instead of unstructured application values. `CommandDefinition` carries a bounded alias list and multiple overloads. A `CommandParameter` accepts either a standard `CommandArgumentType` or a named `CommandEnum`; hard enums provide fixed choices and soft enums provide replaceable suggestions. `UpdateSoftEnumPacket` performs bounded add, remove, or replace updates by enum name. The packet codec deduplicates shared tables deterministically, validates every enum and alias reference, and rejects duplicate names, conflicting definitions, unknown flags and indexes, and oversized tables. Postfix, constraint, and chained-subcommand tables remain closed until their complete semantic models are needed. Client suggestions carry no command authority; parsing, permissions, player resolution, execution, output audience, and plugin dispatch belong to Bedriox.

Bidirectional packet 93 carries a bounded `PlayerSkin` value alongside its authenticated player UUID and the current new/old skin-name fields. Bedriox accepts this normal appearance synchronization only for the spawned session's authenticated identity.

The player-list skin binding retains the verified login `ProfileHash` and serializes the current string-valued trusted-skin flag. Available actor identifiers are generated as bounded network NBT from the actor types the server can actually spawn. `PalettedStorage`, `ChunkSectionData`, `ChunkColumnData`, and `ChunkSerializer` form the generic full-column boundary: callers supply runtime-ID palettes and X-Z-Y indexes, contiguous signed-Y sections, one biome storage for every dimension section, and optionally bounded network-NBT block-entity roots. The serializer chooses the smallest supported `1/2/3/4/5/6/8/16`-bit layout, uses padded words where Bedrock requires them, emits v9 absolute section Y, and applies safe biome copy-last framing. Border blocks are always encoded with a zero count because non-empty Education border arrays are unsafe for retail clients. The fixed-flat factory delegates to this same serializer while preserving its qualified conservative two-bit biome form. Requested later empty sections use the all-air result, and both height maps use protocol 2193's sixteen length-prefixed 16-byte pieces. Chunk caching and blob IDs remain disabled.

Client-data verification retains the signed token's bounded, self-reported `DeviceOS` as a private `DeviceOs` value. Signature verification proves which authenticated client supplied the claim, not that the physical-device claim is truthful. Peer-facing `PlayerListAddEntry` and `AddPlayerPacket` use the distinct current `BuildPlatform` wire enum; undefined value `0` is rejected, and callers that intentionally avoid device disclosure use `BuildPlatform::Unknown` (`-1`).

`ChunkColumnData` requires its included block sections to start at `minSectionY` and remain contiguous through the highest transmitted section. Its biome list covers the complete declared `minSectionY..maxSectionY` range even when no block sections are transmitted. Each block and biome storage contains exactly 4,096 cells; block sections may contain up to eight layers. Runtime IDs must already have been translated for the active protocol by the consumer. `ChunkSerializer::section()` can also serialize one generic section for a SubChunk response.

`InteractPacket` recognizes the current vehicle-exit, mouseover, NPC-open, and inventory-open action domain (`3` through `6`) and preserves the optional target position. In particular, the ordinary inventory notification is the exact three-byte payload `06 00 00` for target runtime ID zero with no position. Unknown actions, partial positions, non-finite coordinates, trailing bytes, and truncations fail deterministically.

`ActorMetadataCollection` provides the one bounded, strictly ascending synchronized-data list used by both `AddPlayerPacket` and `SetActorDataPacket`. Supported values are byte, little-endian short, ZigZag integer, little-endian float, bounded UTF-8 string, ZigZag long, and three little-endian float vectors. `PlayerActorMetadata::baseline()` emits the complete initialized player snapshot: semantic visibility, climbing, breathing, collision (bit 48), and affected-by-gravity (bit 49) flags; the second flag word; health, color, nametag, full air and maximum air, leash state, scale, standing dimensions, always-visible nametag, zero freezing strength, and the player collision-box vector. The adjacent bit 47 is `LINGER` and must not be substituted for collision. `AddPlayerPacket` embeds that snapshot when a peer first becomes visible; later `SetActorDataPacket` instances carry state changes. Actor-property collections remain explicitly unsupported and must be empty.

`PlayerAuthInputPacket` exposes the current input-data indexes through `PlayerAuthInputFlag` while retaining the bounded raw integer list for wire inspection. `hasInput()` performs typed membership checks; `jumpHeld()`, `jumpPressed()`, and `jumpReleased()` distinguish held and edge-triggered jump state. Horizontal and vertical collision values are client hints only and never authoritative collision results. `predictedVelocity()` names the packet's Pos Delta field accurately: it is the client's predicted velocity at the end of that input tick, not a trusted displacement. The unsigned `tick` remains an `UnsignedLong`; consumers can use `UnsignedLong::compareTo()` for monotonic admission without lossy signed conversion. Protocol 2193 encodes the input-data count and each optional action with one presence marker.

`CorrectPlayerMovePredictionPacket` (161) is the protocol-2193 server-with-rewind response for rejected client movement. It preserves the prediction type, finite position/delta/rotation values, the current independently optional angular-velocity field, authoritative on-ground state, and the unsigned processed input tick. Protocol 2193 inherits this layout for both player and vehicle prediction; an angular velocity of zero is therefore valid for a player correction. `MovePlayerMode::RESPAWN` names mode 1 according to the current packet schema. `MovePlayerPacket` always writes the protocol-2193 teleport-metadata presence marker after the riding actor ID, requires it to agree with `TELEPORT` mode, and writes teleport cause and source fields only when that marker is present.

`MovementPredictionSyncPacket` (322) is the current serverbound movement-property notification. It preserves the complete 131-bit current actor-flag domain as a canonical bounded large VarInt, three finite bounding-box values, speed, underwater speed, lava speed, jump strength, health, hunger, three retained finite unknown values, an unsigned runtime actor ID, and the flying marker. The codec requires exact payload termination and rejects noncanonical or overflowing flags and actor IDs, non-finite floats, invalid booleans, and truncation. Decoding only establishes a typed protocol value; it does not authorize changes to movement, collision, abilities, health, hunger, or any other server-owned state.

Input data may be empty, which projects to an empty flag list. Known flags are unique and bounded to the current 66-entry domain. Item interaction, stack request, block action, vehicle rotation, and predicted-vehicle fields each use one current optional discriminator. Block-action lists and packed item-use transactions decode into bounded typed values; their inventory actions retain the typed source, slot, before-stack, and after-stack rather than only a count. Unsupported action variants, vehicle payloads, and malformed conditional presence fail closed. The packed item descriptor has one optional signed stack-network-ID VarInt after its presence boolean; no additional variant discriminator exists in protocol 2193. Outbound encoding rejects flags whose required conditional payload is not implemented.

`InventoryTransactionPacket` (30) provides a state-free typed boundary for the current normal, mismatch, item-use, item-use-on-entity, and item-release variants. It caps inventory actions at 100, legacy slot sets at 1,024, each legacy byte list at 89 bytes, and item user data at 100 KiB. Request-ID-dependent legacy presence, source container/flag presence, every enum, finite vectors, descriptor scalar ranges, exact termination, and all list and byte lengths are validated before a value is returned. Decoding does not authorize an inventory mutation; Bedriox remains responsible for rejection and simulation policy.

The item-use conversation retains both current client entry points. Standalone packet 30 carries the typed place, use, destroy, and attack actions plus trigger, hand, selected slot, item descriptor, positions, prediction, and cooldown state. Packet 144 retains its bounded embedded item-use projection. A click-air `Use` value is only an intent: authoritative use starts when no item is active, while a later click-air intent may attempt completion. Item-release action `Release` ends a releasable use; value `1` is named `Consume` to match the wire meaning but is not treated as proof that food was consumed. The server must compare the selected authoritative stack and active-use session before mutating state, then correct rejected predictions.

`InventoryContentPacket` (49) sends up to 128 typed network item descriptors followed by the required full-container name and storage item. Its existing integer slot-count constructor remains available and preserves the retail-qualified empty snapshot bytes; `emptySlot()` exposes that same established descriptor to typed snapshot builders. `InventorySlotPacket` (50) sends one authoritative slot correction with independently optional full-container-name and storage-item values in the exact current order. Both values have exact, bounded decoders for fixture and consumer verification. `ItemStackResponsePacket` (148) writes every affected slot with the protocol-2193 optional positive stack-network ID, custom name, optional filtered name, and durability correction; an empty authoritative slot omits its stack-network ID. `FullContainerName` bounds the protocol-2193 container-name ID and optional little-endian dynamic ID. These clientbound packets describe server-owned state only; they do not make client inventory claims authoritative.

Persistent storage conversations use `ContainerOpenPacket::blockInventory()` for the byte-sized server window ID, typed screen kind, and authoritative block position. `ContainerClosePacket` now carries the same closed `ContainerType` domain in both directions. `ContainerSlotType` names all 67 current full-container-name values, including level-entity storage, shulker boxes, barrels, and dynamic containers; `FullContainerName::slotType()` returns that closed value without exposing an unnamed wire number. `ContainerRegistryCleanupPacket` (317) releases up to 128 full-container registry entries and validates every optional dynamic ID.

`BlockActorDataPacket` (56) projects one signed block position followed by exactly one structurally validated network-NBT compound. Network NBT is capped at 1 MiB, 32 levels, 65,536 entries, 65,536 collection elements, and 65,536 bytes per string before traversal or allocation; duplicate compound keys, unknown tags, negative or excessive collections, truncation, and trailing data fail closed. The little-endian factory converts the server's canonical block-entity NBT before projection. `BlockEventPacket` (26) carries a typed state-change event and signed event data; `containerState()` names the established open/closed animation shape used by storage blocks. Decoding either packet communicates state only and never authorizes a world or inventory mutation.

Routine spawned-client coverage includes typed, closed codecs for `PlayerActionPacket` (36), `ContainerOpenPacket` (46), `ContainerClosePacket` (47), the exact-empty `ServerSettingsRequestPacket` (102), `NetworkStackLatencyPacket` (115), and `RequestAbilityPacket` (184), in addition to `MobEquipmentPacket` (31), `AnimatePacket` (44), and `ClientCacheStatusPacket` (129). Mob equipment carries the shared bounded `InventoryItemStack`, three unsigned slot/container bytes, and an unsigned actor runtime ID. Its canonical empty descriptor has a zero item ID and zero stack size; decoding non-empty equipment remains a notification and grants no inventory authority. Container-open retains the unsigned dynamic container ID, the closed current signed container-type domain, signed block position, and signed actor unique ID; `mainPlayerInventory()` selects type `INVENTORY` (`-1`) at `(0,0,0)` without inventing authority. A decoded server-settings request is only a notification and does not imply a response. `PlayerActionType` exposes the current action domain and retains both block positions and the face as untrusted notification data. `BlockPosition` bounds every coordinate to signed 32-bit wire space. Player action and ability requests never grant authority by being decoded.

Player equipment synchronization uses packet 31 for both hands and packet 32 for armor. `InventoryContainerId` names the fixed inventory (`0`), offhand (`119`), armor (`120`), hotbar (`122`), fixed-inventory (`123`), UI (`124`), and registry (`125`) window values. The packet-32 snapshot is an unsigned actor runtime ID followed by helmet, chestplate, leggings, boots, and body network item descriptors in that exact order. It is registered bidirectionally because current clients may emit it, but a decoded client snapshot remains notification-only. `FullContainerName` separately names armor (`6`) and offhand (`34`) for stack-request and correction projections. Moving equipment can therefore be reconciled through the already registered item-stack request/response and inventory content/slot packets without granting client-owned item state authority.

`UpdateAttributesPacket::nutrition()` sends bounded `minecraft:player.hunger` and `minecraft:player.saturation` values in `0..20`, with a default saturation of `20`. Exhaustion remains server-only and is not synchronized as a player attribute. Actor events `UseItem` (`9`) and `EatingItem` (`57`) cover the current visual item-use notifications; they do not prove that an authoritative use or consumption succeeded.

`EmoteListPacket` (152) is available in both directions and preserves the actor runtime ID plus a list of canonical emote-piece UUIDs. The list is capped at 4,096 entries before allocation, each UUID is structurally validated, and truncation or trailing data fails deterministically. Decoding this packet communicates no authority and does not prescribe whether the runtime stores or broadcasts the advertised list.

`EmotePacket` (138) preserves the actor runtime ID, bounded UTF-8 emote/XUID/platform strings, unsigned tick duration, and the two known flag bits as typed values. It is a bidirectional notification; decoding a request does not authorize broadcast. `LevelEventPacket` (25) still admits the signed open event-ID domain, while `LevelEventType` and the packet factories name the protocol-2193 start, stop, and update break events; block destruction with or without sound; crack particles; and the six face-specific block-punch particles. Their data remains an already-translated block runtime ID or event-specific progress value selected by the consumer. `UpdateBlockPacket` (21) carries a signed block position, already-translated unsigned runtime ID, the five known update flags, and an unsigned layer. Level events and block updates are clientbound output surfaces here; world mutation and audience selection remain server responsibilities. All three codecs require exact payload termination and reject unknown flag bits.

`LevelSoundEventPacket` (123) carries the current bounded SoundEvent serialize-name string, finite position, signed event-specific data, bounded identifier, baby and relative-volume-disabled flags, fixed little-endian actor unique ID, and optional finite fire position. `LevelSoundEventName` keeps the serialize-name domain open and bounded while providing verified `hit`, `break`, and `place` constants and factories. Sound choice, block runtime data, audience, and whether an event should be emitted remain server responsibilities.

`RemoveActorPacket` (14) carries exactly one signed VarLong actor unique ID. It removes the matching peer actor from a client's world view; world membership, audience selection, player-list removal, and disconnect cleanup remain server responsibilities. Its decoder rejects truncated, overflowing, non-canonical, and trailing data.

`MoveActorAbsolutePacket` (18) is the peer-actor movement surface. It carries an unsigned actor runtime ID, the four current typed header flags (on-ground, teleported, force-move, and force-completion), three finite position floats, and pitch/yaw/head-yaw byte angles. Unknown header bits, non-finite coordinates, malformed variable integers, truncation, and trailing bytes fail closed. `SetActorDataPacket::playerPosture()` composes sneaking and sprinting with the complete baseline player flags, ensuring a posture update cannot accidentally clear breathing, collision, gravity, name, or climbing behavior.

Dropped-item visibility uses the closed packet conversation formed by `AddItemActorPacket` (15), `MoveActorDeltaPacket` (111), `TakeItemActorPacket` (17), and the existing `RemoveActorPacket` (14). Add-item carries signed/unsigned actor identities, one bounded network item descriptor, finite position and velocity, ascending typed metadata, and the fishing-source marker. Delta movement uses protocol 2193's independent optional position and byte-angle fields, four required boolean state markers, and its trailing unsigned tick. Take-item identifies the item and collector by unsigned runtime IDs. These values do not allocate entities, authorize pickups, or select recipients.

`SetActorMotionPacket` (40) carries one unsigned actor runtime ID, a finite three-float velocity, and the required unsigned client tick. The protocol value does not decide damage, reach, cooldown, knockback, or audience; those remain authoritative server behavior.

`TextPacket` (9) is represented by bounded packet values for each admitted protocol-2193 union shape. `ChatPacket` carries an untranslated `CHAT` author and message, `SystemTextPacket` carries an untranslated `SYSTEM` message, and `TranslatedTextPacket` carries a translation key plus at most 16 bounded parameters. `TextPayloadVariant` and `TextPacketType` own the wire discriminators; mismatched translation markers, variants, types, malformed optional filters, oversized strings or parameter lists, truncation, and trailing data fail closed. Server policy decides recipients, localization keys, and whether a message should be emitted.

Container identifiers retain their unsigned wire byte; `signedContainerId()` exposes the conventional `-1` sentinel without changing the encoded value. A latency packet preserves its full unsigned 64-bit creation time and the schema-defined `fromServer` flag; `serverResponse()` produces the corresponding server-marked value, but response policy belongs to the runtime. `AnimatePacket::isSwing()` identifies an ordinary swing notification without prescribing broadcast behavior. Request-ability values retain their typed unset, boolean, or float discriminator, accept the current ability-index domain `0..19` including vertical fly speed, reject index `20`, and require a finite float. The survival ability factory declares all current capabilities in its set mask and supplies all three speed floats, while enabling only ordinary survival interaction bits `0..5`; flying, may-fly, no-clip, and speed-capability bits are not ability values. The server may safely ignore requests or return its authoritative state.

`InteractPacket` accepts the bounded action-byte domain `0..6`. Established Bedrock implementations and retail traffic use both compact ordinal and retained legacy-valued notifications. The minimal runtime treats every decoded interaction as a notification-only no-op, so this conservative domain does not grant interaction authority. Target ID, optional position, finite floats, and exact payload termination remain mandatory.

The movement projection and standalone packet 147 retain complete typed take, place, swap, drop, destroy, consume, create, mine-block, creative-craft, recipe-craft, automatic-craft, optional-craft, repair/disenchant, loom, retained no-payload, and advisory-result requests. The values preserve bounded amounts, full source and destination container names, byte slots, signed durability predictions, fixed little-endian stack-network IDs, recipe and creative entry IDs, requested craft counts, bounded ingredient descriptors, and action-specific fields. Both packet forms preserve bounded filter strings and the optional text-processing origin, while the legacy request-ID projection remains available to consumers. `ItemStackResponsePacket` encodes protocol-2193 success or error entries; successful entries may carry authoritative affected slots grouped by full container name, including requested/actual slots, count-dependent stack-network IDs, redactable custom names, and bounded durability correction. These values describe intent and reconciliation only; Bedriox owns validation, atomic mutation, stack-ID allocation, and rejection sync. Packet 307 `SetPlayerInventoryOptionsPacket` remains notification-only.

`CreativeContentPacket` (145) carries bounded typed groups and entries. Each group uses the current one-byte `CreativeItemCategory`, a bounded name, and a network item-instance icon; each entry has a unique positive creative network ID, an item instance, and a zero-based reference to a declared group. The item instance retains its count, unsigned auxiliary damage value, translated network block runtime ID, and up to 100 KiB of bounded item user data. That user-data envelope carries per-stack NBT and placement or break restrictions without making Protocol responsible for gameplay interpretation. Item-definition component NBT remains a separate packet-162 concern. Canonical `minecraft:*` block states are a Data and server identity; Protocol deliberately receives only the runtime ID translated for the active packet boundary.

The complete creative selection conversation is registered in both forms used by the current client: standalone `ItemStackRequestPacket` (147) and the request embedded in `PlayerAuthInputPacket` (144). It admits the bounded creative selection, created-output marker, advisory craft-results descriptor, and ordinary transfer actions, while `ItemStackResponsePacket` (148) carries the authoritative success or correction. Creative network IDs remain unsigned 32-bit values selected by the server, and packet construction rejects zero, duplicate, or dangling IDs. Full-content emission does not add authority to any client-reported descriptor, auxiliary value, NBT, block runtime ID, or stack-network ID.

`GameType` closes the current seven-value game-mode domain for packet 62 and `UpdatePlayerGameTypePacket` (151), whose latter form also carries the signed actor unique ID and unsigned tick. `RequestPermissionsPacket` (185) retains the fixed little-endian actor ID, typed player permission, and unsigned-short custom permission bits. Decoding any of these packets does not grant game mode, inventory, or permission authority.

No external implementation code or fixture bytes are incorporated. Successful unit vectors and schema conformance do not by themselves qualify a retail client; Bedriox owns that end-to-end qualification.
